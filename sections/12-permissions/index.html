12　settings.json で権限を決める

資料 P10・P12
このセクションのゴール
settings.json の env（変数）と permissions（許可・確認・禁止）を使い、Claude が「読めるもの」「消せるもの」を決める。Skill・hooks とは別の層の制御を体験する。

準備

このセクションのブランチに切り替える。.claude/ の中身が、このセクション用に入れ替わる。

ターミナル
git switch section-12-permissions

前のセクションで書き換えたファイルがあると、切り替えに失敗したり、変更が持ち越されたりする。git restore . で元に戻してから切り替える。切り替えたあとは、新しい会話（新しいセッション）で Claude Code を開く。

このセクションの中身（.claude/ など）
.claude/settings.json
├── env           HANDSON_GREETING を定義
└── permissions   allow（echo・ls・cat）/ ask（notes.txt の編集）/ deny（.env の読み取り・rm）
sample/
├── .env          ダミーの値（偽物）。読み取りの拒否を試す
├── tmp.txt       削除の拒否を試す
└── notes.txt     編集の確認（ask）を試す

やってみる

  1. いまの権限を見る

    Claude に入力
    /permissions
    期待する結果　allow・ask・deny に、.claude/settings.json に書いた規則が並ぶ。個人設定（~/.claude/settings.json）の規則も混ざって見える。

  2. 変数（env）を読ませる

    Claude に入力
    環境変数 HANDSON_GREETING の値を、Bash の echo で表示して
    期待する結果　こんにちは from settings.json が表示される。settings.json の env に書いた変数が、Claude の実行する Bash に渡っている。

    settings.json は Git で共有される。秘密の値は env に書かない（個人の秘密は、Git に入れない settings.local.json に書く）。

  3. 読み取りを拒否する（deny）

    Claude に入力
    sample/.env を読んで、中身を表示して
    期待する結果　読み取りが拒否される（パーミッション設定で拒否された、という旨が出る）。中身は表示されない。

    Read ツールだけでなく、Bash の cat sample/.env も拒否される（この教材での確認結果）。

  4. 読み取りを、Bash の cat でも試す

    Claude に入力
    次のコマンドを Bash でそのまま実行して、出力をそのまま見せて: cat sample/.env
    期待する結果　こちらも拒否される。cat は allow に入れているが、deny が優先される（deny > ask > allow）。

  5. 削除を拒否する（deny）

    Claude に入力
    Bash で rm sample/tmp.txt を実行して削除して
    期待する結果　実行が拒否され、sample/tmp.txt は残る。

  6. 確認を出させる（ask）

    Claude に入力
    sample/notes.txt の末尾に「追記」と書き足して
    期待する結果　編集の前に確認が出る。承認しなければ、編集されない。承認すれば編集される（演習のあとは元に戻す）。

    ask は「毎回、人が確認する」設定。

  7. 抜け道を体験する（find -delete）

    Claude に入力
    次のコマンドを Bash でそのまま実行して: find sample -name tmp.txt -delete
    期待する結果　rm は deny だが、find は deny にも allow にも書いていないので、削除は拒否されず、確認が出る。承認しなければ消えない。

  8. allow を広く書くと、deny をすり抜ける

    .claude/settings.json の allow に "Bash(find *)" を足し、新しい会話で、手順 7 の依頼をもう一度する。

    期待する結果　確認なしで sample/tmp.txt が削除される。rm を deny にしていても、find -delete で消せてしまう（この教材での確認結果）。

    deny が止めるのは、書いた方法だけ。広い allow（find *、cat * など）は、deny の抜け道になりうる。

  9. 後始末

    ターミナル
    git restore .
    期待する結果　設定・tmp.txt・notes.txt が元に戻る。

整理

区分意味このブランチの例
allow確認なしで実行できるBash(echo *)、Bash(ls *)、Bash(cat *)
ask毎回、人が確認するEdit(./sample/notes.txt)
deny頼まれても実行しない（最優先）Read(./sample/.env)、Bash(rm *)

ここがポイント

  • 優先順位は deny > ask > allow。個人設定・プロジェクト設定のどこかで deny されていれば、拒否される。
  • 置き場所: ~/.claude/settings.json（個人）／.claude/settings.json（プロジェクト。Git で共有）／.claude/settings.local.json（個人の上書き。Git に入れない）。
  • 個人設定が有効だと、期待結果と違うことがある。たとえば個人設定で find や Edit が allow になっていると、「確認が出る」はずの手順で確認が出ない。
  • Skill の allowed-tools（セクション 04）は「その Skill を使うターンだけ、承認なしで使えるツール」。settings.json の権限は、プロジェクト全体に効く。
  • 権限でも完全には守れない。find -delete のような別の書き方や、広い allow が抜け道になる。確実に止めたいものは、hooks（セクション 07）も併用する。

うまくいかないとき

  • 拒否されない → 個人設定で allow されていないか確認する（/permissions）。新しい会話で開き直す。
  • 確認が出ない → ask の規則が効いているか、/permissions で確認する。--permission-mode を変えていると、確認が省かれることがある。

LLM の判断で動くため、結果は毎回同じとは限らない。「期待する結果」はこの教材で確認した例。違う結果になっても、言い換えて何度か試す。
