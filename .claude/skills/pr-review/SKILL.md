# PR レビュー

このリポジトリのプルリクエストをレビューし、結果を PR にコメントとして投稿する。

## 手順

1. **変更範囲を把握する**

   ```bash
   git diff origin/main...HEAD --stat
   git diff origin/main...HEAD
   ```

2. **必要に応じて周辺コードを読む** — 差分だけでは判断できない場合のみ。変更されていないファイルを網羅的に読む必要はない。

3. **下の観点に沿ってレビューする**

4. **PR に日本語でコメントを投稿する** — 出力形式に従うこと。

## レビュー観点

優先度の高い順に確認する。

### 1. 正しさ

- ロジックの誤り、境界値の扱い漏れ（0 除算、空配列、`undefined`）
- 非同期処理の待ち忘れ、例外の握りつぶし
- DOM 要素の取得失敗を考慮していない箇所（`src/main.ts` 系）

### 2. テスト

- 追加・変更されたロジックにテストがあるか
- 異常系（例外を投げるケース）が検証されているか
- テストの期待値がロジックの再実装になっていないか

### 3. TypeScript

- `any` や不必要な型アサーション（`as`）
- 型を絞り込めるのに `if` で握りつぶしている箇所
- `strict` を無効化するような回避策

### 4. CI・ビルド

- ワークフローの変更が意図どおりか（トリガー、権限、Node バージョン）
- `pnpm-lock.yaml` の更新漏れ

## 出力形式

```markdown
## レビュー結果

<全体の要約を1〜2文>

### 指摘事項

- **`ファイル名:行番号`** — <指摘内容と、なぜ問題かの理由>
```

- 指摘は**具体的なファイルと行**に紐づけること。
- **指摘がない場合**は「## レビュー結果」と「特に問題は見つかりませんでした。」だけを書く。無理に指摘を作らない。

## やらないこと

- 些細なスタイルの好み（命名の揺れ、インポート順、フォーマット）は指摘しない
- 変更されていない既存コードの問題は指摘しない
- コードを修正しない。レビューコメントの投稿までが仕事
- 「〜も検討してはいかがでしょうか」のような曖昧な提案を並べない。問題があるなら理由を添えて断言する
