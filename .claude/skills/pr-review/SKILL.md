# PR レビュー

このリポジトリのプルリクエストをレビューし、結果を PR にコメントとして投稿する。

## 手順

引数として対象 PR の場所（`owner/repo/pull/番号` 形式）が渡される。
往復回数には上限がある。1回のコマンドで済むものをまとめ、無駄な確認を挟まないこと。

1. **変更範囲を把握する** — 1コマンドで取得する

   ```bash
   git diff origin/main...HEAD --stat && git diff origin/main...HEAD
   ```

2. **周辺コードを読むのは、差分だけで判断できない場合のみ** — 多くても2〜3ファイルまで。変更されていないファイルを網羅的に読まない。差分に十分な情報があるならこの手順は飛ばす。

3. **レビュー結果を PR に投稿する** — 出力するだけでは不十分。必ず投稿まで完了させること。

   ```bash
   gh pr comment <PR番号> --body "<レビュー結果>"
   ```

   特定の行に紐づく指摘は `mcp__github_inline_comment__create_inline_comment` を使ってもよい。
   いずれの場合も、レビュー結果を分割して複数回投稿せず1回にまとめる。

## レビュー観点

優先度の高い順に確認する。

### 1. 正しさ

- ロジックの誤り、境界値の扱い漏れ（0 除算、空配列、`undefined`）
- 非同期処理の待ち忘れ、例外の握りつぶし
- DOM 要素の取得失敗を考慮していない箇所（`src/main.ts` 系）

### 2. テスト

- 追加・変更されたロジックにテストがあるか
- 異常系（例外を投げるケース）が検証されているか
- テストの期待値がロジックの再実装になっていないか

### 3. TypeScript

- `any` や不必要な型アサーション（`as`）
- 型を絞り込めるのに `if` で握りつぶしている箇所
- `strict` を無効化するような回避策

### 4. CI・ビルド

- ワークフローの変更が意図どおりか（トリガー、権限、Node バージョン）
- `pnpm-lock.yaml` の更新漏れ

## 出力形式

```markdown
## レビュー結果

<全体の要約を1〜2文>

### 指摘事項

- **`ファイル名:行番号`** — <指摘内容と、なぜ問題かの理由>
```

- 指摘は**具体的なファイルと行**に紐づけること。
- **指摘がない場合**は「## レビュー結果」と「特に問題は見つかりませんでした。」だけを書く。無理に指摘を作らない。

## やらないこと

- 些細なスタイルの好み（命名の揺れ、インポート順、フォーマット）は指摘しない
- 変更されていない既存コードの問題は指摘しない
- コードを修正しない。レビューコメントの投稿までが仕事
- 「〜も検討してはいかがでしょうか」のような曖昧な提案を並べない。問題があるなら理由を添えて断言する
